# Hangfire PostgreSql learnings

Moved from CLAUDE.md. Read before touching `BackgroundJobConfiguration.cs`.

### Hangfire PostgreSql `EnableTransactionScopeEnlistment` — Real Production Risk, Not Local-Only

`Hangfire.PostgreSql.PostgreSqlStorageOptions.EnableTransactionScopeEnlistment` **defaults to `true`** in the library itself — the app's config (`BackgroundJobConfiguration.cs`) was just leaving that default in place, not deliberately opting in. It makes every Hangfire storage write enlist in an ambient `System.Transactions.TransactionScope`, so a Hangfire client call (enqueue, state change, etc.) can participate in the same transaction as application code that also opens a `TransactionScope`. **No code anywhere in this app does that** (`grep -rl TransactionScope src/Neba.Api` matches only this one config line) — the flag had zero consumers and was pure unexamined risk.

**The failure mode, found while hand-testing `/legacy/ping` in `aspire run`:** the local Postgres container was restarted (via `docker restart`) while the API process was still running with an open connection/ambient transaction. Afterward, the API's *single* Hangfire worker (dev's `Hangfire:WorkerCount` is `1`, see below) got permanently wedged — Hangfire's own slow-log watchdog reported it as stuck inside `Audit.Hangfire.AuditJobExecutionFilterAttribute.OnPerforming` for 400+ seconds and climbing, for whichever job it happened to dequeue next (confirmed on two different, otherwise-unrelated jobs across two separate reproductions). The console logs showed why: `Npgsql.Transaction` was stuck in a **tight, endless retry loop** — `warn: Npgsql.Transaction[31010]` dozens of times, then `fail: Npgsql.Transaction[31003] Exception during single-phase transaction rollback (local ID=...)`, repeating forever with the *same* local transaction ID. `pg_prepared_xacts` on the server was empty, confirming this is a **client-side** Npgsql/`System.Transactions` retry loop that never gives up trying to resolve a transaction whose connection is gone — not a server-side orphaned two-phase-commit transaction.

**Isolated repro ruled out Azurite/network/DNS as the cause**: constructing the exact same `TableClient` (used by the Hangfire job-execution audit filter's `AzureTableDataProvider`) with the app's real connection string and calling `CreateIfNotExists()` synchronously, standalone, completed in 51ms with no hang. The hang only reproduces when the ambient `TransactionScope` (from `EnableTransactionScopeEnlistment`) has been orphaned by a Postgres connection loss first — the audit filter's Azure Table write isn't the root cause, it's just the thing that happens to be running on the sole worker thread when the retry loop starves the process.

**Is this local-only, or a real production risk?** Real production risk, not local-only. The trigger here was a manual `docker restart` of the dev Postgres container, but the same client-side condition (API process stays up, underlying Postgres connection is lost or reset mid-transaction) is exactly what happens during an Azure Database for PostgreSQL planned-maintenance restart or an HA failover — neither requires the app itself to restart. What's local-only is the *symptom that made it obvious*: dev's `Hangfire:WorkerCount: 1` (`appsettings.Development.json`, deliberately set low in commit `95358de1` to constrain local resource usage) meant one wedged job stopped *100%* of local job processing instantly. Production (`appsettings.json`) runs `WorkerCount: 3`, so the same event there would silently consume one of three workers rather than halting everything outright — degraded, not dead, but each recurrence of this event permanently and irreversibly eats another worker until none are left, since the retry loop never resolves and the worker never comes back. It also compounds: repeated app-process/Postgres restart cycles during this investigation left ~110 orphaned Postgres backend processes on the local container (exhausting `max_connections=100`, `53300: sorry, too many clients already`) — that accumulation is a local artifact of manual restart cycling, not something expected from a single production failover, but it illustrates how invisible and cumulative this class of failure is until something else (health checks, connection limits) surfaces it.

**Fix applied**: `EnableTransactionScopeEnlistment = false`, set explicitly in `BackgroundJobConfiguration.cs` (with a comment explaining why) rather than left as an unexamined default. This removes the entire failure mode at its source — Hangfire's PostgreSql storage falls back to plain Npgsql transactions for its own writes, with no ambient `System.Transactions` machinery to get orphaned. Low risk: nothing in the app was relying on the enlistment behavior.

**Not changed, but worth knowing**: dev's `Hangfire:WorkerCount: 1` is what turned this into a total local outage instead of a partial one — that's a deliberate resource-constraint choice from commit `95358de1`, not an oversight, so it was left alone rather than silently bumped. If a similar issue resurfaces in dev and total blockage makes it hard to tell "one stuck job" from "everything is broken," consider temporarily raising it to 2–3 to match production's posture.

**Secondary, related observation (not the root cause, but adjacent)**: the Hangfire job-execution audit filter's `.DataProvider(new AzureTableDataProvider(...))` (in the same `AddAuditJobExecutionFilter(...)` config) uses a raw, un-wrapped provider — it bypasses `Neba.Api.Auditing.ResilientAuditDataProvider`, the decorator every other audit path in the app goes through to degrade a storage outage into a logged warning instead of failing the caller. `ResilientAuditDataProvider` only catches thrown exceptions, though — it has no timeout, so it would not by itself have prevented this specific hang. Still, it means a slow-but-eventually-throwing Azure Table Storage outage on this one path fails differently (and less gracefully) than everywhere else in the app. Not fixed here since it's a separate concern from the transaction-enlistment bug and wasn't the cause of the incident — flagged for whoever next touches `BackgroundJobConfiguration.cs`'s audit wiring.
