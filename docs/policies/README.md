# Authorization Policies

Reference for every ASP.NET Core authorization policy registered in the system. See [ADR-0008](../adr/0008-policy-documentation-structure.md) for why this exists and how it's structured.

Source of truth is code — this table describes it for reviewers and help-doc authors:

- Policies are registered in `src/Neba.Api/Security/SecurityConfiguration.cs` (and mirrored in `src/Neba.Website.Server/Account/AccountConfiguration.cs` for Blazor `<AuthorizeView>` use).
- Permissions are defined in `src/Neba.Api.Contracts/Security/Permission.cs`.
- Roles and their permission grants are defined in `src/Neba.Api/Security/Domain/Roles.cs` / `src/Neba.Api/Security/Infrastructure/SecurityRoleSeeder.cs`.

## Policies

| Policy | Kind | Satisfied by | Enforced at | Details |
| --- | --- | --- | --- | --- |
| `Authenticated` | Static | Any signed-in user (no specific permission/role) | `LogoutEndpoint`, `GetCurrentUserEndpoint`, `ChangePasswordEndpoint` (`POST /security/password/change`; acts only on the caller's own account, taken from the token) | [change-password.md](../help/change-password.md) |
| `Permission:{value}` | Dynamic (one per `Permissions` value, resolved by `PermissionPolicyProvider`) | Caller holds the single named permission claim (e.g. `Permission:Read`, `Permission:News.DeleteArticle`, `Permission:System.EditUser`) | Any endpoint calling `.Policies(Permissions.X.PolicyName)` | — |
| `CanManageArticles` | Static, OR-of-many | Any permission in `Permissions.ArticleManagementPermissions` (`News.CreateArticle` or `News.DeleteArticle`) | Registered via `AddNebaPolicies()` (API and Website); drives status-badge visibility only in `ArticleCard.razor`, `NewsDetail.razor`, `NewsList.razor` — every actual page/action (Create Article, Delete) gates on the specific `Permission:News.CreateArticle` / `Permission:News.DeleteArticle` policy matching its own endpoint, not this one | [can-manage-articles.md](can-manage-articles.md) |
| `CanManageSponsors` | Static, OR-of-many | Any permission in `Permissions.SponsorManagementPermissions` (`Sponsors.CreateSponsor` or `Sponsors.EditSponsor`) | Registered via `AddNebaPolicies()` (API and Website); drives Active/Inactive badge and Inactive Sponsors section visibility only in `Sponsors.razor` and `SponsorDetail.razor` — the Create/Edit Sponsor pages and actions gate on the specific `Permission:Sponsors.CreateSponsor` / `Permission:Sponsors.EditSponsor` policy matching their own endpoint, not this one | [can-manage-sponsors.md](can-manage-sponsors.md) |
| `CanManageTournaments` | Static, OR-of-many | Any permission in `Permissions.TournamentManagementPermissions` (`Tournaments.CreateTournament`, `Tournaments.ManageTournamentSponsors`, `Tournaments.EditTournament`, `Tournaments.DeleteTournament`, `Tournaments.ManageTournamentStatus`) | Registered via `AddNebaPolicies()` (API and Website); consumed via `User.HasAnyPermission(PermissionCatalog.TournamentManagementPermissions)` in `GetTournamentEndpoint.cs` and `ListTournamentsInSeasonEndpoint.cs` — every individual tournament action still gates on its own specific `Permission:{value}` policy (e.g. `Permission:Tournaments.CreateTournament`) in addition to this OR-set. | — |
| `CanUploadTournamentLogo` | Static, OR-of-many | Any permission in `Permissions.TournamentLogoUploadPermissions` (`Tournaments.CreateTournament`, `Tournaments.EditTournament`, or `Tournaments.EditTournamentLogo`) | Registered via `AddNebaPolicies()`; gates `UploadTournamentLogoEndpoint` (`POST /tournaments/logo`), which stages the file for create, full edit, or logo-only edit. Staging alone changes no tournament: the file only attaches through a command that passes the logo claim check. The logo edit itself gates on the specific `Permission:Tournaments.EditTournamentLogo` policy (`EditTournamentLogoEndpoint`, `LogoEditButton.razor`), so a per-user denial of that permission removes the edit. `EditTournamentEndpoint` also refuses a changed logo for a caller with a stored denial of `Tournaments.EditTournamentLogo` (403); the denial is read from the store through `IPermissionDenialReader`, not from the JWT, and a role that merely lacks the permission is not a denial. | [edit-tournament-logo.md](../help/edit-tournament-logo.md) |
| `CanUploadSeriesLogo` | Static, OR-of-many | Any permission in `Permissions.SeriesLogoUploadPermissions` (`Series.CreateSeries`, `Series.EditSeries`, or `Series.EditSeriesLogo`) | Registered via `AddNebaPolicies()`; gates `UploadSeriesLogoEndpoint` (`POST /series/logo`), which stages the file for create, full edit, or logo-only edit. Staging alone changes no Series. The logo-only edit gates on the specific `Permission:Series.EditSeriesLogo` policy. The Series write permissions are per action and do not cover payouts (a later phase adds its own permission). | [edit-series-logo.md](../help/edit-series-logo.md) |
| `Permission:Series.CreateSeries` | Dynamic (single permission) | Caller holds `Series.CreateSeries`; seeded to Admin (through `Permissions.List`) and Manager | `CreateSeriesEndpoint` (`POST /series`); the Series list shows the create button only when the user holds it | [create-series.md](../help/create-series.md) |
| `Permission:Series.EditSeries` | Dynamic (single permission) | Caller holds `Series.EditSeries`; seeded to Admin, Webmaster and Manager | `EditSeriesEndpoint` (`PUT /series/{id}`); `GetSeriesAdvancementEndpoint` (`GET /series/{id}/advancement`); `ListStageSquadsEndpoint` (`GET /series/{id}/stages/{stageId}/squads`); `RecomputeSeriesAdvancementEndpoint` (`POST /series/{id}/stages/{stageId}/recomputations`); `PickStageSquadEndpoint` (`PUT /series/{id}/stages/{stageId}/squad`); the Series page shows the edit button only when the user holds it. The endpoint refuses a changed logo (403) for a caller with a stored denial of `Series.EditSeriesLogo`; the denial is read from the store through `IPermissionDenialReader`, not from the JWT. The permission does not cover payouts | [edit-series.md](../help/edit-series.md) |
| `Permission:Series.DeleteSeries` | Dynamic (single permission) | Caller holds `Series.DeleteSeries`; seeded to Admin and Manager | `DeleteSeriesEndpoint` (`DELETE /series/{id}`); the Series page shows the delete button only when the user holds it | [delete-series.md](../help/delete-series.md) |
| `Permission:Series.EditSeriesLogo` | Dynamic (single permission) | Caller holds `Series.EditSeriesLogo`; seeded to Admin and Manager | `EditSeriesLogoEndpoint` (`PUT /series/{id}/logo`); works on a locked Series; the Series page shows the edit-logo button only when the user holds it, so a per-user denial removes it | [edit-series-logo.md](../help/edit-series-logo.md) |
| `Permission:Series.ManageAdvancement` | Dynamic (single permission) | Caller holds `Series.ManageAdvancement`; Admin (through `Permissions.List`) and Webmaster (seeded); Manager is not seeded | `ListStageResultsEndpoint` (`GET /series/{id}/stages/{stageId}/results`); `CreateStageOverrideEndpoint` (`POST /series/{id}/stages/{stageId}/overrides`, kind Add or Clear) and `RemoveStageOverrideEndpoint` (`DELETE /series/{id}/stages/{stageId}/overrides/{overrideId}?version=n`); the Series page shows the override actions only to holders | (help doc with the UI phase) |
| `Permission:HallOfFame.EditHallOfFamePhoto` | Dynamic (single permission) | Caller holds `HallOfFame.EditHallOfFamePhoto`; seeded to Webmaster, Manager, and Journalist | `UploadHallOfFamePhotoEndpoint` (`POST /hall-of-fame/photos`) and `EditHallOfFamePhotoEndpoint` (`PUT /hall-of-fame/{id}/photo`); the Hall of Fame page shows the edit-photo button only when the user holds it | — |

## When to update this file

- **New policy added** (a new `AddPolicy(...)` call): add a row here. If it's a straightforward single-permission or single-role check, the row is enough — no dedicated file needed.
- **New policy has real nuance** (OR/AND-of-many semantics, exceptions to explain, reasoning a reviewer would otherwise have to reverse-engineer from `SecurityConfiguration.cs`): add a dedicated `docs/policies/<policy-name>.md` and link it from the row.
- **Existing policy's semantics change** (e.g. a permission added to `ArticleManagementPermissions`): update the row and, if one exists, the dedicated file.
